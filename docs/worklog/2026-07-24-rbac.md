## 0. 스코프

- **무엇:** GUEST(미인증)/USER/SUSPENDED/ADMIN 4역할 게이트. 재사용 가능한 authorize 프리미티브(`requireActiveUser`/`requireAdmin`/`requireActiveBearer`), 로그인·OAuth로그인·refresh 회전의 SUSPENDED 세션발급 초크포인트, 기존 인증 라우트의 실시간 SUSPENDED 차단 리트로핏, 데모 admin 라우트(`GET /api/admin/ping`).
- **왜:** 지금까지(#1) 인증은 "로그인했는가"만 봤다 — 정지된 계정이라도 기존에 발급받은 세션/토큰이 살아있으면 계속 쓸 수 있었다. 신뢰(trust)의 최종 원천을 DB로 옮기고, 정지가 걸리자마자(±토큰 만료를 기다리지 않고) 실시간으로 막아야 중고거래 플랫폼의 제재가 실효를 가진다. 이후 서브프로젝트(#3~#7)가 리소스 소유권 권한을 얹을 기반이기도 하다.
- **결정:** 서브에이전트 구동(SDD), 태스크 3개, 브랜치 하나(`feat/rbac`, 새 브랜치 생성/전환/머지 금지). 카덴스: 태스크 1(프리미티브+초크포인트)·2(라우트 적용)는 🔴 적대적 리뷰+fix루프(보안 핵심), 태스크 3(E2E+워크로그, 본 문서)은 🟢. 마이그레이션 없음(Role enum은 #1에 이미 존재). SUSPENDED 판정 원천은 **access 토큰의 role이 아니라 매 요청 DB에서 새로 읽는 role**(토큰은 최대 15분 stale일 수 있어 신뢰하지 않는다).

## 2. E2E 테스트 목록과 결과 (`e2e/rbac.spec.ts`, 4개 테스트)

관리자 API로 role을 바꿀 방법이 아직 없다(#6 범위 — 태스크 브리프에 명시). 그래서 SUSPENDED/ADMIN 시나리오는 브리프가 명시적으로 승인한 방식대로, **이번 실행이 만든 unique 닉네임 유저에 한해** `docker compose exec -T db psql -U app -d app -c "UPDATE \"User\" SET role='...' WHERE nickname='...'"`를 스펙 파일 안에서 `node:child_process`의 `execFileSync`로 직접 실행한다(별도 스크립트 분리 없이, Playwright 테스트가 Node 프로세스에서 도는 성질을 그대로 이용). psql로 인라인 삽입하는 값은 `unique()`가 만드는 영숫자(시간 base36 + 난수) 닉네임뿐이라 별도 이스케이프 없이도 인젝션 위험이 없다.

1. **GUEST(세션 없음): 보호 라우트는 전부 401 UNAUTHENTICATED** — ✅. 쿠키 없는 최상위 `request` 픽스처로 `GET /api/admin/ping`과 `PATCH /api/profile/bio` 둘 다 401 + `code:"UNAUTHENTICATED"`.
2. **일반 USER: admin/ping은 403 FORBIDDEN, 일반 mutating 라우트(bio)는 200** — ✅. register→login 후 같은 세션으로 `GET /api/admin/ping` → 403 `FORBIDDEN`(인증은 통과했지만 role 불충분 — GUEST의 401과 구분됨), `PATCH /api/profile/bio` → 200.
3. **SUSPENDED(psql UPDATE): 같은 세션이 실시간으로 403 차단되고, refresh·재로그인도 403** — ✅, 이 서브프로젝트의 헤드라인 기능을 실제로 psql까지 거쳐 증명한 테스트. 순서: (a) 정지 전 `PATCH /api/profile/bio` 200 확인(베이스라인), (b) `docker compose exec` psql로 해당 유저만 `role='SUSPENDED'`로 변경, (c) **로그아웃하지 않은 동일 세션 쿠키**로 다시 `PATCH /api/profile/bio` → 403 `ACCOUNT_SUSPENDED`(세션/쿠키 자체는 여전히 "유효"하지만 DB-fresh role 조회가 즉시 막음 — 토큰 stale 15분을 기다리지 않는 실시간성), (d) `POST /api/auth/refresh` → 403 `ACCOUNT_SUSPENDED`(회전 거부 + 이 호출이 세션 자체를 폐기), (e) 같은 이메일/비번으로 `POST /api/auth/login` 재시도 → 403 `ACCOUNT_SUSPENDED`(계정 없음과 구분되지 않는 일반 `AUTH_FAILED`가 아니라, 인증 자체는 통과한 뒤의 명시적 정지 코드 — 설계상 의도된 비대칭: 정지는 인증 후 판정이라 열거 오라클이 아니다).
4. **ADMIN(psql UPDATE): admin/ping이 200을 돌려준다(선택 시나리오)** — ✅. 같은 psql 경로로 role만 `ADMIN`으로 바꾼 뒤 `GET /api/admin/ping` → `{ok:true, role:"ADMIN"}`.

psql로 만진 행은 이번 실행이 방금 만든 unique 닉네임 2건(SUSPENDED 1건, ADMIN 1건)뿐임을 실행 후 `SELECT nickname, role FROM "User" WHERE nickname LIKE 'e2e%' ORDER BY "createdAt" DESC LIMIT 15`로 직접 확인했다(6절).

## 4. 검토 중점(설계 D절 대응)

1. **SUSPENDED 두겹 차단** — ✅. (1) 초크포인트: `login.ts`/`oauth/link.ts`/`session.ts`가 정지 유저의 새 세션 발급·회전을 거부(태스크 1, 유닛으로 증명). (2) 실시간: `requireActiveUser`를 쓰는 모든 라우트가 매 요청 DB fresh role을 봐서 기존에 살아있는 세션으로도 즉시 막는다(태스크 2 유닛 + 본 태스크 E2E 테스트 3이 실 세션·실 DB로 재증명 — 로그아웃하지 않은 채로 바로 403).
2. **DB fresh role** — ✅. `loadActive`가 매번 `db.user.findUnique`로 role을 다시 읽고 토큰의 role은 전혀 참조하지 않는다(태스크 1 유닛: "토큰은 USER를 주장, DB는 SUSPENDED" 케이스가 403). E2E도 같은 성질을 실증: 세션 쿠키(발급 시점엔 USER)를 그대로 둔 채 DB만 psql로 바꿨는데 즉시 403.
3. **에러마스킹** — ✅. RBAC 실패는 `FORBIDDEN`/`ACCOUNT_SUSPENDED`/`UNAUTHENTICATED` 코드만 노출(`withErrorHandling`/`toClientError` 기존 그대로 재사용, RBAC 전용 신규 에러경로 없음). 정지 유저의 오비번 로그인은 여전히 일반 `AUTH_FAILED`(정지 사실보다 먼저 비번 검증이 실패하면 계정 존재/정지 여부를 구분 못 함 — 열거 방지). `grep -rn "console.log" src/features/auth/rbac.ts src/app/api/admin` → 매치 0건.
4. **공개라우트 회귀없음** — ✅. `git diff`로 `profile/[nickname]`(공개 프로필), `health`, `login/register/refresh/logout`, `2fa/verify-login`·`resend`·`check-availability`, `oauth start/callback` 등은 태스크 2에서 변경분 없음을 확인(task-2-report 3절). 본 E2E 스위트(29개, health·auth·oauth 포함)가 전부 그린이라는 것 자체가 공개 경로 회귀 없음의 실행 증거이기도 하다.
5. **교차유저 disable fix** — ✅. 태스크 2 적대적 리뷰가 찾아낸 실 결함(2FA disable이 다른 유저의 남은 step_up 쿠키를 받아줌)을 다른 step-up 라우트와 동일한 userId 일치검사로 막고, 근본 원인(logout/withdraw가 step_up/2fa_challenge 쿠키를 안 지움)까지 고쳤다(commits 67a21b4, 26fe6de). 회귀 테스트(`2fa/disable/route.test.ts`)로 커버됨 — 본 태스크가 새로 재검증하지는 않았으나(스코프가 E2E+워크로그로 한정) 전체 유닛 그린에 포함돼 계속 지켜지고 있음을 확인.
