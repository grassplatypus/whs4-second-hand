## 2. 태스크 10: E2E에서 드러난 편차 3건 (설계 대비, 모두 `e2e/auth.spec.ts` 내에서 처리, `src/` 미변경)

1. **`unique()` 헬퍼 길이 vs `nickname` 스키마 상한.** 브리프 원문 `` `e2e-${Date.now()}-${Math.floor(Math.random()*10_000)}` ``는 20~22자가 되는데, Task 4에서 이미 리뷰·머지된 `registerSchema.nickname`은 `max(20)` — 실측 결과 이 조합의 가입은 거의 항상(90%+) 400 `INVALID_INPUT`으로 실패함(수동 curl로 confirm). `src/features/auth/schema.ts`를 고치는 건 범위 밖(태스크 10은 `src/` 수정 금지)이라, 헬퍼를 `` `e2e${Date.now().toString(36)}${Math.floor(Math.random()*1000)}` ``(13~14자, "-other" 접미사 붙여도 20자 이내)로 축약. 유일성·시간+난수 기반 성질은 그대로 유지.
2. **Playwright 기본 Accept-Language.** 이 머신의 헤드리스 Chromium 컨텍스트가 기본으로 `en-US` 계열 Accept-Language를 보내고, `src/i18n/request.ts`(Task 6 설계: 쿠키→Accept-Language→`defaultLocale`)가 이를 "영어 선호"로 해석 — 쿠키 없는 첫 방문에서 "기본은 한국어" 가정이 깨져 `/signup` 첫 로드가 영어로 렌더됨. curl로 confirm(Accept-Language 없음/`ko` → 한국어, `en-US` → 영어). 실제 타깃 사용자(한국 브라우저)를 재현하도록 `test.use({ locale: "ko-KR" })`를 스펙에 추가.
3. **Next.js route-announcer의 `role="alert"` 충돌.** Next가 접근성용으로 심어두는 `__next-route-announcer__` div도 `role="alert"`라, 로그인 실패 메시지의 `role="alert"` `<p>`와 함께 `getByRole("alert")`가 strict-mode에서 2개 요소에 매치 — 문구로 필터링(`.filter({ hasText: ... })`)해 우리 쪽 배너만 가리키도록 좁힘.

이 세 가지 모두 `src/` 코드의 결함이 아니라 (a) 테스트 리터럴이 이미 머지된 스키마 제약을 감안하지 못했거나, (b) 테스트 실행 환경(브라우저 기본 로케일)과 앱의 로케일 폴백 순서 간 상호작용, (c) 프레임워크가 심는 접근성 엘리먼트와의 셀렉터 충돌 — 이므로 `e2e/auth.spec.ts` 안에서만 수정했다.

## 3. DoD 8개 항목 검증 결과

1. **가입 → DB 암호문+blind index 저장(평문 없음), 비번 bcrypt** — ✅. `docker compose exec -T db psql -U app -d app -c 'SELECT "emailCiphertext","emailBlindIndex","phoneCiphertext","passwordHash" FROM "User" LIMIT 3;'` → 4개 컬럼 모두 `iv.tag.ciphertext`(AES-GCM) / HMAC 다이제스트 / `$2b$10$...`(bcrypt)만 보임, 평문 이메일·전화·비밀번호 전무.
2. **중복 이메일/닉네임 가입 차단, 중복체크 API 동작** — ✅. E2E `register → login → ... → logout`에서 동일 이메일 재가입이 409 `EMAIL_TAKEN` 확인(Task 5 유닛테스트가 `NICKNAME_TAKEN`/동시 P2002 케이스까지 커버).
3. **로그인 성공 시 access JWT + HttpOnly refresh 쿠키 발급** — ✅. Task 6 구현·수동검증(`set-cookie: refresh_token=...; HttpOnly; SameSite=Lax`) + E2E `loggedIn.ok()`/`accessToken` 확인.
4. **refresh 회전 동작, 재사용 시 family 폐기+401** — ✅. Task 7 CAS 클레임으로 원자화, 유닛테스트(패밀리 전체 `updateMany`) + 수동검증(옛 쿠키 재사용 → `AUTH_FAILED` 401, 새로 회전된 세션도 함께 폐기됨을 `psql`로 확인)로 검증. E2E는 정상 회전 1회(`refreshed.ok()`)와 로그아웃 후 재사용 거부(`afterLogout.status()===401`)를 확인.
5. **인증 이벤트 감사로그 기록, 로그/에러에 PII 평문 없음** — ✅. `docker compose exec -T db psql -U app -d app -c 'SELECT * FROM "AuthAuditLog" LIMIT 5;'` → 컬럼은 `id/userId/event/ip/ua/createdAt`뿐. `grep -rn "console.log" src/features/auth src/app/api/auth` → 출력 없음. 유일한 `console.error`(`audit.ts:40`)는 `{event, userId, err}`만 로그.
6. **`/signup` `/login` 페이지 한/영 동작(E2E)** — ✅. `signup page renders in Korean and switches to English`, `login page shows a friendly failure message` 모두 통과(단, Chromium 기본 로케일 이슈로 `test.use({ locale: "ko-KR" })` 필요 — 위 2절 참고).
7. **전체 테스트 통과, 에러 마스킹 유지** — ✅. `pnpm test` 20 파일/122개 전부 통과, `pnpm exec tsc --noEmit` 클린, `pnpm build` 성공(`/api/auth/*`, `/login`, `/signup` 전부 동적 라우트로 컴파일). E2E 6/6 통과(재실행 2회 모두 안정).
8. **PIPA 준수 체크리스트 대조 통과** — ✅. `docs/compliance/regulation-comparison.md` 4절에 Keep 8항목 대조 기록(파기는 "부분(설계대로)" — soft delete 컬럼+로그인 차단만 구현, 전체 탈퇴 플로우는 1c로 이관).
