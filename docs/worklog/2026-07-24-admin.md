## 2. 적대적 리뷰(태스크 2) — 발견과 수정

서비스 초안은 목 테스트 15개를 통과했으나 opus 적대적 리뷰가 **1 Important + 3 Minor**를 잡았다. 보안 핵심(권한남용 방지·감사 actor 기록·PII 최소화·snapshot 격리·인젝션)은 전부 통과.

- **Important — 신고 목록 정렬 버그:** `MongoChatRepo.listReports`가 `limit`을 **open-우선 재정렬 전에** 걸었다. status 필터 없이 limit을 주면, 오래된 미처리(open) 신고가 최신 처리완료 건에 밀려 잘려나가 관리자 큐에서 사라진다(T&S에서 진짜 신고가 묻힘). InMemory 트윈은 open-우선 정렬 후 slice라 올발랐다(같은 계약, 반대 동작). **수정:** Mongo를 aggregation 파이프라인으로 — `$addFields`로 open-rank(open=0) 계산 → `$sort {_openRank, createdAt:-1}` → `$limit` → `$project`로 rank 제거. DB에서 정렬·limit이 일관.
- **Minor — 없는 신고 처리 시 거짓 감사:** `resolveReport`가 `updateReportStatus`(없으면 no-op)를 부르고 무조건 감사 로그를 남겨, 존재하지 않는 신고를 "처리함"으로 기록. **수정:** `updateReportStatus`가 matched 여부(boolean) 반환 → 서비스가 false면 404, 감사 안 남김.
- **Minor — 대시보드 count 비효율:** `openReports`를 `listReports({status:'open'}).length`로 세어 open 신고 문서(원문 snapshot 포함)를 전부 메모리에 적재. **수정:** `countReports(status)`(Mongo `countDocuments`) 추가, 정수만 반환.
- **Minor(defer) — suspend TOCTOU:** role read와 update 사이 비트랜잭션. 이 코드베이스에 동시 role 승격 경로가 없어 실현 불가 — 승격 기능 생기면 재검토.

수정 후 26테스트(admin+repo) 그린.

## 3. E2E 목록과 결과 (`e2e/admin.spec.ts`, 5개)

**환경:** 대시보드 openReports·신고 목록이 Mongo를 쓰므로(채팅 이원화 계승) Postgres+Mongo 둘 다 필요. Mongo 컨테이너가 호스트 미발행이라 socat 사이드카로 릴레이(채팅 E2E와 동일). 관리자 승격·유저 id 조회는 로컬 db psql(관리자 role 전환 API가 없는 건 의도 — E2E 스캐폴딩).

1. **인가** — GUEST 대시보드 401, 일반 USER 403, ADMIN 200(집계 수치 존재). ✅
2. **제재** — 정지 전 유저 bio 200 → **자기 정지 400** → 유저 정지(세션 그대로여도 DB-fresh로 즉시 bio 403) → **이미 정지 409** → 해제(bio 200 복구) → **다른 관리자 정지 403 CANNOT_SANCTION_ADMIN**. ✅
3. **강제 삭제** — 관리자가 남의 상품 soft-delete → 공개 조회 404, 재삭제 404. ✅
4. **신고 관리** — 구매자가 판매자(유저) 신고 → 관리자 open 목록에 targetUserId·사유 노출 → 그 id로 정지(판매자 bio 403) → resolve(open서 사라지고 resolved에 등장) → 없는 신고 처리 404. ✅
5. **분쟁 목록** — 분쟁 에스크로가 관리자 disputes 목록에(양측 닉네임·상품·금액) → 관리자 조정(release, #5 라우트 재사용) → 상품 SOLD → 목록서 사라짐. ✅

## 5. 검토 중점 대응(설계 E절)

1. **인가** — ✅. 전 라우트 `requireAdmin`(DB-fresh role), 페이지 `requireAdminPage()`(비관리자 리다이렉트, 방어심층 — 라우트가 독립 강제). E2E: GUEST 401·USER 403·ADMIN 200.
2. **권한 남용 방지** — ✅. 자기 정지 400·다른 관리자 정지 403·이미 정지 409, 대상 USER/SUSPENDED만(선검사가 DB 로드보다 먼저). E2E 재증명.
3. **감사** — ✅. 모든 상태 변경(suspend/lift/forceDelete/resolve/dismiss)이 `AuthAuditLog`에 actor(adminId)를 userId로, 대상을 event 문자열로 기록. 없는 신고엔 거짓 감사 안 남김(리뷰 수정).
4. **신고 원문 격리** — ✅. snapshot(원문)은 관리자 `listReports`만 반환 — 참여자 채팅 경로(toDelivered)는 rawText strip(#4). 리뷰가 non-admin 경로 유출 없음 확인.
5. **PII 최소** — ✅. listReports/listDisputedEscrows/dashboard의 Prisma select는 닉네임·id·수치만(이메일/전화/좌표 복호화 안 함, 스프레드 없음). 관리자 화면 id 노출은 설계 허용(정지 액션에 필요).
6. **강제 삭제** — ✅. soft-delete(deletedAt), 감사, 이미 삭제 404(이중쓰기 없음), 하드삭제 없음.

## 9. 최종 whole-branch opus 리뷰 (base 2a80fc1 → head 93e0128, 29파일 +2274)

판정: **머지 가능(Critical/Important 0)**. 8개 초점(전 surface 인가·권한남용 방지·targetUserId 노출·snapshot 격리·감사 무결성·신고큐 정렬·PII 최소·모듈 드리프트) 전부 통과.

**핵심 확인:**
- 전 8라우트 첫 문장이 `requireAdmin`(GUEST 401/USER·SUSPENDED 403), 페이지는 `requireAdminPage()`로 렌더 전 리다이렉트 + REST 독립 게이트(페이지 우회해도 데이터 못 읽음).
- actor는 항상 `requireAdmin().userId`에서 — 바디 위조 adminId 무시(라우트 테스트 증명).
- `targetUserId` 노출은 관리자 surface(`/api/admin/reports`)에서만·user 신고만·message는 null·이메일/전화 동반 없음(grep 확인). 신고된 유저 정지에 필요·격리됨.
- snapshot(원문)은 관리자 listReports만 — 참여자 경로 `toDelivered`가 rawText strip, #6 변경이 참여자 반환을 넓히지 않음.
- 감사: 성공 뮤테이션당 1행(actor=adminId), 모든 no-op은 감사 전에 throw(없는 신고 404·감사 없음 end-to-end 확인).
- Mongo listReports 파이프라인이 `_openRank` 정렬 **후** limit(태스크2 수정 확인), InMemory 트윈 일치.

**리뷰 반영 수정:** 대시보드 activeEscrows에서 DISPUTED 제외(disputedEscrows와 이중계상 방지 — 두 카드 disjoint). Minor(이미 처리된 신고 재처리 시 중복 감사·200 — UI 도달 불가, 직접 API만) defer, 내비 링크(전역 내비 자체가 없어 moot) 해당 없음.
