# 워크로그 — #4 채팅(상품 기준 1:1 실시간 채팅, WS+Mongo)

기록 원칙: 시간순, 각 항목은 **무엇을 / 왜 / 결정 / 편차·이슈**. 결과보다 결정의 흐름을 남긴다.

## 0. 스코프

- **무엇:** 상품 기준 1:1 채팅. 저장소는 Mongo(대화/메시지/차단/신고), WS 서버(`src/server/ws`)는 실 JWT 인증+참여자 전용 룸, REST(Next API)는 이력·시작·차단·신고, 한국어 비속어/우회 감지·마스킹, 차단·신고, 참여자 격리(제3자 403·PII 없음).
- **왜:** #3(상품)까지는 판매자-구매자가 만날 접점이 상품 상세뿐이었다 — 실제 거래(#5 에스크로)로 이어지려면 그 전에 1:1로 조율할 채널이 있어야 한다. 중고거래 특성상 채팅에는 개인정보(전화번호 등)와 비속어가 실릴 위험이 커서, "상대 닉네임만 노출"과 "원문 비속어를 절대 전달하지 않는다"가 이 서브프로젝트의 핵심 신뢰 요구사항이다.
- **결정:** 서브에이전트 구동(SDD), 태스크 7개, 브랜치 하나(`feat/chat`, 새 브랜치 생성/전환/머지 금지). 카덴스: 필터·서비스·WS인증(태스크 2·3·4)은 🔴 적대적 리뷰(보안/정확성 핵심), repo·라우트·UI·E2E(태스크 1·5·6·7, 본 문서)는 🟢 메인 점검. **저장소 이원화**(채팅=Mongo, 나머지=Postgres) — 새 저장소를 얹는 결정이라 `ChatRepo` 인터페이스로 추상화하고 단위테스트는 `InMemoryChatRepo` fake만 쓴다(실 Mongo 불요, E2E만 실 Mongo 필요).

## 2. E2E 테스트 목록과 결과 (`e2e/chat.spec.ts`, 2개 테스트)

**Mongo 호스트 접근성 이슈와 해결(중요한 환경 편차):** `docker-compose.yml`의 `mongo` 서비스는 `expose: ["27017"]`만 선언돼 있고 `ports:`로 호스트에 게시하지 않는다(컨테이너 간 통신만 전제 — `web`/`ws` 서비스가 컨테이너 네트워크 안에서 `mongo:27017`로 접속). 이번 태스크의 E2E는 `next dev`를 호스트(도커 밖)에서 직접 띄우므로(이전 워크로그들의 관행과 동일), `mongodb://localhost:27017`로 직접 접속을 시도하면 `ECONNREFUSED`가 난다(직접 확인함). **`docker-compose.yml`은 수정 권한이 없어**, 대신 임시 프록시 컨테이너 하나를 추가로 띄웠다: `docker run -d --rm --name grass-mongo-proxy --network grasssecondhand_default -p 127.0.0.1:27017:27017 alpine/socat TCP-LISTEN:27017,fork,reuseaddr TCP:mongo:27017` — 기존 `mongo` 컨테이너/compose 설정은 전혀 건드리지 않고, 같은 도커 네트워크에 붙어 호스트의 27017을 컨테이너의 `mongo:27017`로 그대로 릴레이하는 사이드카일 뿐이다. 이후 `next dev`/`playwright test`는 `MONGO_URL=mongodb://localhost:27017/chat`(env.ts 기본값과 동일한 형태, `.env`의 `mongo:27017`을 오버라이드)로 실행했다. **다음에 이 E2E를 다시 돌리는 사람은 이 프록시(또는 동등한 호스트→컨테이너 포트포워딩)가 필요하다** — 이건 이번 태스크가 남기는 알려진 환경 갭이다(7절에 재기재).

1. **판매자는 자기 상품에 채팅을 시작할 수 없다(SELF_CHAT 400)** — ✅. 판매자가 위치 설정 후 상품을 등록하고, 같은 세션으로 자기 상품에 `POST /api/chat/conversations` → 400 `SELF_CHAT`.
2. **채팅 슬라이스 전체(구매자/판매자/제3자 3개 브라우저 컨텍스트)** — ✅. 순서대로:
   - 구매자가 채팅 시작(첫 텍스트) → 201, `conversationId` 발급, 응답 텍스트가 원문 그대로(마스킹 없음)임을 확인. 구매자의 `GET /api/chat/conversations` 목록에 이 대화가 나타나고 상대는 판매자 **닉네임만**(다른 필드 없음) 노출.
   - 구매자가 "저 진짜 시발 화나네요"를 보냄 → 201이지만 `masked:true`이고 응답 `text`에 "시발" 리터럴이 없음. `GET .../messages`로 다시 조회해도 원문이 어디에도(`rawText` 필드 포함) 새지 않음.
   - 상대(판매자)가 아직 한 번도 답하지 않은 상태에서 구매자가 이미지 전송 시도 → 400 `IMAGE_BEFORE_REPLY`.
   - 판매자가 텍스트로 답장 → 201(이 응답의 `senderId`로 판매자의 실제 `userId`를 확보 — 대화 목록/메시지 어디에도 상대의 userId를 직접 노출하는 필드가 없어, 실제로 보낸 메시지의 `senderId`를 통해 얻는 것이 정상적인 경로).
   - 판매자가 답장한 **이후에는** 구매자가 실제 멀티파트 업로드(`POST /api/products/images`)로 얻은 `imagePath`로 이미지 전송 → 201, `kind:"image"`.
   - 대화 비참여자인 제3의 유저가 이 대화의 `GET .../messages` → 403 `FORBIDDEN`(참여자 격리).
   - 구매자가 판매자를 차단(`POST /api/chat/block`) → 판매자의 전송 시도 → 403 `BLOCKED`(양방향 체크). 구매자가 차단 해제(`POST /api/chat/unblock`) → 판매자가 다시 전송 성공(201).
   - 구매자가 아까의 비속어 메시지를 신고(`POST /api/chat/report`, `targetType:"message"`) → 200 `{ok:true}`.
   - **GUEST(쿠키 자체가 없는 별도 브라우저 컨텍스트)**로 대화 시작/목록조회/메시지조회/차단/신고 5개 엔드포인트 전부 → 401 `UNAUTHENTICATED`.
   - 대화 목록 + 메시지 목록 JSON을 합쳐 구매자/판매자 이메일, 전화번호(하이픈 포함/제거 두 형태 모두)가 전혀 없음을 확인.
   - **페이지 레벨**: 구매자로 `/chat`에 접속 → 제목("채팅") + 판매자 닉네임이 목록에 렌더되는지 확인. `/chat/[id]`로 이동 → 판매자 닉네임 헤딩 + "상품 보기" 링크가 실제로 렌더되는지 확인. 페이지 HTML 어디에도 "시발"(원문 비속어)·이메일이 없음도 확인.
   - **WS**: 이 페이지는 액세스 토큰을 아직 클라이언트에 저장하지 않아(태스크 6 결정) `ChatRoom`이 WS 연결을 아예 시도하지 않는다 — REST 경로가 이미 전체 흐름을 실증했으므로 별도 WS E2E는 추가하지 않았다. WS 서버 자체의 인증 미들웨어(무효/부재 토큰 거부)·참여자 전용 join·마스킹 브로드캐스트는 `src/server/ws/{chat,server}.test.ts`의 실 socket.io 통합 유닛 테스트가 이미 커버한다(태스크 4).

## 4. 검토 중점(설계 검토중점 대응 — WS 실인증·참여자격리·첫메시지/이미지-후-답장 규칙·비속어 마스킹·PII 없음·저장소 이원화)

1. **WS 실인증** — ✅. 태스크 4 적대적 리뷰(commit 4cea9ab)에서 accept-all 스텁을 실제 `verifyAccessToken` 기반 미들웨어로 교체, 무효/부재 토큰은 `next(new Error(...))`로 연결 자체를 거부함을 실 socket.io 통합 테스트로 증명. 본 태스크는 이 성질을 재검증하지 않고 유닛 그린에 포함됨만 확인했다(E2E는 REST 경로만 사용 — 액세스 토큰을 클라이언트가 아직 저장하지 않아 브라우저에서 WS를 시작할 방법이 없다, 4·6절에 명시).
2. **참여자 격리** — ✅ 이중으로 증명. (a) 서비스: `assertParticipant`가 buyer/seller가 아니면 무조건 403(태스크 3 유닛). (b) 본 태스크 E2E: 실 세션 3개(구매자/판매자/제3자)로 제3자의 `GET .../messages`가 실제로 403 `FORBIDDEN`을 받는지 실 Mongo 위에서 재증명(2절 테스트 2). WS의 참여자 전용 join은 실 socket.io 통합 테스트(태스크 4)가 커버.
3. **첫메시지/이미지-후-답장 규칙** — ✅. 원 설계(DoD#3, "첫 메시지 멀티미디어 차단")는 태스크 6에서 사용자 요구로 더 엄격한 규칙(`IMAGE_BEFORE_REPLY` — 상대가 한 번이라도 답하기 전까지는 몇 번째 메시지든 이미지 금지)으로 대체됐다. 본 E2E가 이 정확한 신규 규칙을 실증: 판매자가 답하기 전 이미지 시도 → 400, 판매자가 답한 **이후에만** 성공(2절 테스트 2).
4. **비속어 마스킹(원문 admin-only)** — ✅. "시발"을 보내면 응답 `masked:true`이고 `text`에 원문 리터럴이 없으며, 참여자에게 반환되는 메시지 객체에 `rawText` 프로퍼티 자체가 없음을 직접 단언(`not.toHaveProperty`). 신고 시 스냅샷에는 원문이 보존된다는 성질은 태스크 3 유닛(리뷰가 찾아낸 결함의 수정분)이 커버 — 이 저장된 원문은 어떤 참여자 대상 API로도 반환되지 않으므로 본 E2E가 "원문이 새지 않는다"는 것만 검증하는 것이 곧 그 성질의 실사용 증거다.
5. **PII 없음** — ✅. 대화 목록(`otherNickname`만, id/이메일/전화 없음)·메시지 목록 JSON을 합쳐 구매자/판매자 이메일·전화번호(하이픈 포함/미포함 두 형태) 부재를 직접 단언. 페이지 HTML(`/chat/[id]`)에도 이메일이 없음을 확인.
6. **저장소 이원화** — ✅. 채팅 전체(대화/메시지/차단/신고)가 실 Mongo(`MongoChatRepo`) 위에서 동작함을 이번 E2E가 실제로 증명(호스트→Mongo 접속 편차는 2절에 기재). 상품/유저/세션 등 나머지는 그대로 Postgres(`prisma`)를 쓰며, 상품 조회(`startConversation`의 `db.product.findFirst`)와 유저 닉네임 조회(`listConversations`)만 Postgres를 넘나든다 — 이 넘나듦 자체도 서비스 함수 시그니처(`db: ChatDb`)로 이미 명시적이다.
7. **WS-live-append best-effort 한계** — ✅ 정직하게 기록. `ChatRoom`은 `accessToken` prop이 없으면(현재 앱의 기본 상태 — 액세스 토큰을 아직 클라이언트에 저장하지 않음) WS 연결을 아예 시도하지 않는다. 즉 지금 배선 상태에서는 **실시간 수신은 전혀 동작하지 않고**, 메시지 송수신은 전부 REST(전송 시 즉시 응답으로 내 화면에 반영, 상대 메시지는 새로고침/재조회로만 보임)로만 이뤄진다. 이것은 설계상 의도된 진행 개선(progressive enhancement)이지 버그가 아니지만, "실시간 채팅"이라는 이름에 비해 현재 사용자 경험은 실시간이 아니라는 점은 명확히 남겨야 한다. WS 서버 자체(인증·룸·브로드캐스트)는 정상 동작하며 유닛으로 커버돼 있다 — 빠진 것은 오직 "브라우저가 토큰을 들고 소켓을 여는" 클라이언트측 배선.

## 5. DoD 7개 항목 검증 결과

1. **WS 실 JWT 인증(미인증 거부), 룸 참여자 격리** — ✅. 태스크 4 유닛(실 socket.io 통합 테스트)으로 증명. 본 태스크에서 재검증하지 않음(E2E는 REST 경로만 사용 — 4절 1번에 이유 명시).
2. **상품 기준 1:1 대화 시작(자기자신·차단 방지), 실시간 송수신** — ✅ 부분. 자기자신 방지(`SELF_CHAT`)는 본 E2E 테스트 1, 차단 방지는 본 E2E 테스트 2(차단 중 전송 403). "실시간" 송수신은 WS 유닛으로만 증명되고 실제 배선은 REST(신뢰 가능한 경로)다 — 4절 7번에 한계 명시.
3. **첫 메시지 멀티미디어 차단** — ✅ (강화된 형태로). `IMAGE_BEFORE_REPLY`로 대체·확장돼 있고 본 E2E가 이 정확한 동작을 실증(4절 3번).
4. **한국어 비속어/우회 감지·마스킹(전달·표시 마스킹본, 원문 관리자용)** — ✅. 태스크 2 유닛(정규화·우회 감지 22테스트) + 본 E2E(실 저장·조회 경로에서 원문 미노출, 4절 4번).
5. **차단(차단 유저 대화·전송 불가), 신고(→#6용 저장)** — ✅. 차단은 본 E2E 테스트 2(차단 중 판매자 전송 403, 해제 후 재개). 신고는 본 E2E(200 확인) + 태스크 3 유닛(스냅샷에 원문 보존).
6. **참여자만 이력/전송, 타인 접근 403, PII 없음** — ✅. 4절 2번·5번.
7. **전체 테스트 통과, UI 한/영** — ✅. E2E 37/37(기존 스펙 전부 회귀 없음 포함), 유닛 753/753, tsc clean, build green(3절). UI 한/영 카탈로그는 태스크 6에서 이미 추가·확인됨(본 태스크는 재검증하지 않고 페이지 렌더만 확인).

## 7. 남은 알려진 갭 (다음 단계로 이관)

- **WS 실시간 배선 부재** — 현재 `ChatRoom`은 액세스 토큰을 들고 있지 않아 WS를 전혀 시작하지 않는다. 진짜 실시간 채팅이 되려면 클라이언트가 액세스 토큰을 안전하게 보관/획득하는 방법(다음 서브프로젝트 또는 별도 태스크)이 먼저 필요하다.
- **Mongo 호스트 게시 부재** — `docker-compose.yml`의 `mongo` 서비스가 `expose`만 하고 `ports`로 호스트에 게시하지 않아, 도커 밖에서 `next dev`를 띄우는 개발/E2E 흐름은 매번 별도의 호스트→컨테이너 포트포워딩(본 태스크는 `socat` 사이드카)이 필요하다. `docker-compose.yml` 수정은 이번 태스크 권한 밖이라 그대로 이관한다.
- **신고 처리·제재 UI/관리자 API 부재** — 설계상 의도된 범위 밖(#6). 이번 태스크는 `POST /api/chat/report`가 저장까지만 하는 것을 확인했다.
- **에스크로/거래 확정** — #5 범위, 다루지 않음.
- **최종 브랜치 opus 리뷰** — #1·#2 계열 서브프로젝트의 선례처럼 태스크 1~7 전체를 가로지르는 교차 리뷰는 아직 수행되지 않았다. 이 워크로그는 태스크 7(E2E)까지의 기록이며, 최종 리뷰는 별도 단계로 남아 있다.
