## 0. 스코프

- **무엇:** 상품 기준 구매자↔판매자 안전거래. 대금을 플랫폼이 잠깐 보관(에스크로)했다가 거래가 확정되면 판매자에게 정산, 틀어지면 구매자에게 반환하는 **상태머신**. 요청→조정(금액 협상)→보관(입금)→정산(수령확인)/반환. 분쟁 접수(참여자)·조정(관리자). 저장은 Postgres(상품·유저와 강결합, 트랜잭션 필요).
- **왜:** #3(상품)·#4(채팅)까지는 구매자-판매자가 "만나서 조율"하는 단계였다. 실제 돈이 오가는 순간의 신뢰가 이 서브프로젝트의 핵심 — "누가 어떤 전이를 할 수 있는가(행위자 인가)", "대금이 이중으로 정산·보관되지 않는가(원자성)", "합의된 금액만 정산되는가(금액 무결성)"가 무너지면 플랫폼이 돈을 잃는다. 그래서 상태머신·서비스는 🔴 적대적 리뷰 대상으로 잡았다.
- **결정:** 브랜치 하나(`feat/escrow`), 태스크 6개. 돈은 **목 보관**(실 PG·실 이체 없음 — 실 SMTP/Kakao가 목인 것과 동일 관례). 지갑 잔액 모델은 도입하지 않음(YAGNI — 상태머신이 핵심이고 충전 흐름은 데모 가치 대비 복잡도 과함). 분쟁 처리 UI·대시보드는 #6, 탈퇴 가드 실규칙은 #7(#5는 `countActiveEscrows` 데이터만 제공).

## 2. 적대적 리뷰가 찾은 실결함(태스크 3) — 이 서브프로젝트의 핵심 사건

서비스 초안은 목 단위테스트 34개를 전부 통과했지만, 목은 **동시성과 실 Prisma SQL 의미**를 구조적으로 재현하지 못한다. opus 적대적 리뷰가 세 가지 실결함을 잡았다:

- **C1(Critical) — 이중 정산/정산·반환 경합.** 정산(`confirm`)·반환(`refund`)·조정(`resolve`)이 에스크로 상태를 `update({ where: { id } })`로만 바꾸고 **from-state를 조건에 걸지 않았다**. 동시 confirm+refund가 각자 사전읽기에서 FUNDED를 보면 둘 다 커밋 → 같은 대금이 판매자에게 정산되고 구매자에게도 반환된다(실 돈이면 플랫폼이 손실). READ COMMITTED(어디에도 isolationLevel 미설정)라 목은 절대 못 잡는다.
- **C2(Critical) — 이중 보관.** `fund`의 이중보관 가드가 트랜잭션 안에 있긴 했으나 비잠금 `SELECT` + 무조건 `UPDATE`라 무력. 두 구매자가 동시에 `fund`하면 둘 다 상품을 RESERVED로 바꾸고 각자 FUNDED가 된다 — 설계가 막으려던 바로 그 이중 보관.
- **I1(Important) — 분쟁 우회.** `confirm`/`refund`가 `assertTransition`에만 의존했는데 `TRANSITIONS[DISPUTED]=[RELEASED,REFUNDED]`라 `DISPUTED→RELEASED/REFUNDED`가 유효로 통과 → 분쟁으로 얼려둔 거래를 **참여자가 관리자 조정을 우회해** 일방 정산·반환할 수 있었다. (`resolveDispute`는 이미 `status==='DISPUTED'`를 명시 검사해 올발랐다 — confirm/refund만 누락.)

**수정(공통 원인 → 공통 처방):** 모든 상태 변경을 **조건부 쓰기(optimistic write)** 로 바꿨다 — `updateMany({ where: { id, status: <기대상태> }, data })` 후 `count===1`이 아니면 409로 트랜잭션 롤백. Postgres가 동일 행 동시 UPDATE를 직렬화하므로, 선점된 쪽은 `WHERE status=...`가 더는 매칭되지 않아 count 0 → 하나만 성공한다. C2는 상품에도 같은 패턴(`where: { id, status:'SELLING', deletedAt:null }`). I1은 confirm/refund에 소스 상태를 `FUNDED`로 명시 제한. 회귀 테스트(동시성 count=0→409, DISPUTED에서 참여자 정산 409, 이중보관 count=0→409) 추가. 42테스트 그린. **교훈:** 상태머신 전이는 "읽고-검사-쓰기"가 아니라 "조건부 쓰기+영향행수 확인"이어야 동시성 안전하다. (M2 — resolve의 서비스단 인가 부재는 설계상 라우트 `requireAdmin` 담당, 라우트 테스트로 커버. M1 — 비정산 전이의 audit 경합은 같은 조건부 쓰기로 함께 처리.)

## 5. 검토 중점 대응(설계 F절)

1. **행위자 인가** — ✅. `loadParticipant`가 모든 참여자 뮤테이션 앞에서 buyer/seller 아니면 403. fund/confirm=구매자, refund=판매자 명시 검사, resolve=`requireAdmin`. 자기수락(`CANNOT_ACCEPT_OWN`)·차례 아님(`NOT_YOUR_TURN`) 차단. E2E가 판매자 입금 403·구매자 반환 403·제3자 403·구매자 resolve 403을 실 세션으로 재증명.
2. **상태머신 무결성** — ✅. 조건부 쓰기(updateMany+count)로 유효 전이만·종착 재전이 불가·이중 정산 불가. E2E: 종착 후 재정산 409.
3. **상품 연동 원자성·이중보관** — ✅. fund/confirm/refund/resolve가 상품+에스크로를 한 `$transaction`으로. fund는 상품 SELLING 조건부 갱신(count 확인)으로 이중보관 차단. E2E: 이중보관 409, 상품 상태 RESERVED/SOLD/SELLING 전이 확인.
4. **금액 무결성** — ✅. 정산은 항상 서버 보관 `escrow.amount`. fund/confirm은 금액 입력 없음. 제안 금액 양수·정수·상한(1e9) 검증. 수락은 비제안자만(자기 제안 자기 수락 금지). E2E: counter 12000 → 최종 정산액 12000.
5. **자기거래 금지** — ✅. E2E: SELF_TRADE 400.
6. **PII/id 유출 없음** — ✅. get/list DTO는 상대 닉네임만 — buyerId/sellerId/lastProposerId/actorId 원본 미노출(이벤트 actor는 me/other/admin으로 매핑). E2E: 상세 JSON에 이메일·전화 부재.

**검토 중점과 결과:**
